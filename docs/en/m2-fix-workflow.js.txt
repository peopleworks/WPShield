**An adversarial review then found working bypasses, measured against the built assemblies.
None were fixed. You are fixing them.**

Every one is a **parser differential**: WPShield's parser and PHP's main/rfc1867.c disagree about
the same bytes, so WPShield inspects one thing and WordPress writes another. That is the central
failure mode for this kind of gateway. Closing a differential means making WPShield **fail closed
whenever it cannot be sure it sees what the backend will see** — never making it imitate PHP's bugs,
which is an arms race WPShield loses.

---

### F1 — CRITICAL. A closing boundary anywhere but the end makes the body invisible.

Body prefixed with one extra line:

    --X--
    --X
    Content-Disposition: form-data; name="f"; filename="shell.php"

    <?php echo 'synthetic marker'; ?>
    --X--

Measured: Status=Complete, Fields=0, Files=[] -> Allow -> **forwarded in Block mode**, no log line
above Information. PHP has no concept of a terminating boundary: find_boundary() scans lines until
one matches --X, and multipart_buffer_headers() drops lines without a colon, so PHP parses the
smuggled part and writes $_FILES['f'].

Cause: MultipartInspectionReader.ReadAsync initialises status = Complete and the loop breaks on
"section is null", which MultipartReader returns the moment FinalBoundaryFound is set. Nothing
verifies the parse consumed the buffer. _stream.Position is useless as a residual check —
BufferedReadStream has already read to EOF (measured position 223 of 223).

Suggested fix: Complete must mean *the parse reached the end of the buffer*. The gateway owns a
seekable buffer, so do a bounded pre-scan for --{boundary} occurrences: if any occurrence exists
after the first --{boundary}--, or anything other than CRLF/LWSP follows the last delimiter, the
status is Malformed. Do NOT infer it from stream position. This deliberately narrows the existing
test PreambleAndEpilogue_AreToleratedAndCountAsNothing (MultipartInspectionReaderTests.cs:782) —
a prose epilogue stays fine, an epilogue containing the delimiter must not.

### F2 — CRITICAL. obs-fold in a part header smuggles a filename.

    --X
    Content-Disposition: form-data; name="f"
     ; filename="shell.php" : x

    <?php echo 'synthetic marker'; ?>
    --X--

Measured: Complete, Fields=1, Files=[] — WPShield sees a *form field*, which is never sampled and
never inspected. A variant keeping a benign filename="photo.jpg" on the first line measured
Files=[photo.jpg]: WPShield inspects and passes photo.jpg, PHP writes shell.php.

Cause: MultipartReader.ReadHeadersAsync splits every line on the first colon regardless of leading
whitespace, so the folded line becomes a junk header named ' ; filename="shell.php" ' and
Content-Disposition keeps its first-line value — so HasRepeatedFileNameParameter cannot see it,
because the duplicate never enters disposition.Parameters. PHP does the opposite and says so in
rfc1867.c: /* space in the beginning means same header */, then keeps the **last** filename. The
trailing " : x" exists only so ASP.NET finds a colon; without it the reader already fails closed.
A tab folds identically.

Suggested fix: reject any part-header key whose first character is SP or HTAB, before
GetContentDispositionHeader(). MultipartReader does not expose raw lines, so derive it from
section.Headers.

### F3 — HIGH. A comma in Content-Type means WPShield never notices the request is multipart.

Measured against the shipped assembly:

    multipart/form-data; boundary=aaa                       Declares=True  Boundary=True   INSPECTED
    multipart/form-data; boundary=aaa,                      Declares=False Boundary=False  NOT INSPECTED
    multipart/form-data; boundary=aaa,bbb                   Declares=False Boundary=False  NOT INSPECTED
    multipart/form-data; boundary=aaa, application/json     Declares=False Boundary=False  NOT INSPECTED
    multipart/form-data;boundary=----WebKitFormBoundaryABC, Declares=False Boundary=False  NOT INSPECTED

Cause: DeclaresMultipartFormData answers "did this declare multipart?" with
MediaTypeHeaderValue.TryParse — a strict whole-value parser that treats comma as a separator. So
the fail-closed pairing in UploadInspectionService (!hasBoundary && !DeclaresMultipartFormData)
yields NotInspected, and the request streams through with no rule running and no buffer. PHP:
boundary_end = strpbrk(boundary, ",;") -> aaa.

This is exactly the hole the [!IMPORTANT] box in docs/en/m2-multipart-inspection.md:32-35 says must
not exist. Note MultipartInspectionReaderTests.cs:945 already carries the string
"multipart/form-data; boundary=aaa, application/json" but only asserts the TryGetBoundary half —
the pairing assertion that would have caught F3 exists only for the duplicate-header case.

Suggested fix: match the media type **textually**, not via a full parse — trim leading whitespace,
take everything up to the first ';', ',' or whitespace, compare ordinal-case-insensitively to
multipart/form-data. Every row above then becomes Malformed -> 415 in Block.

### F3b — HIGH, same class. Duplicate and prefix boundary parameters.

TryGetBoundary rejects duplicate Content-Type *header lines*, and HasRepeatedFileNameParameter
rejects a doubled filename, but the same differential in the boundary parameter is accepted:

  - multipart/form-data; boundary=aaa; boundary=bbb   — WPShield takes the first.
  - multipart/form-data; xboundary=bbb; boundary=aaa  — WPShield gets aaa; PHP's
    strstr(ct, "boundary") matches inside xboundary and gets bbb.

Confirmed with a probe that one body can be valid multipart under both aaa and bbb, yielding
photo.jpg (Complete, no findings, forwarded) to WPShield and shell.php to the other reading.

Suggested fix: mirror HasRepeatedFileNameParameter — reject more than one boundary parameter, and
reject when the raw value contains the substring "boundary" more times than there are real boundary
parameters.

### F4 — HIGH. The rules model NTFS normalization, not WordPress normalization.

NormalizedFileName approximates what **Windows** writes. On the plugin endpoints WPShield exists to
defend, the function that decides the final name is WordPress's sanitize_file_name(), which
**deletes** ? [ ] / \ = < > : ; , ' " & $ # * ( ) | ~ ! { } % + and chr(0) — plus the ASCII
backtick, which is in the set too — collapses whitespace
and hyphen runs, then trim($filename, '.-_'). A name inert under NTFS rules becomes executable
under WordPress's.

Measured through the real eight-rule engine with the real 4096-byte sample truncation:

    sent='shell.php'    -> WP writes 'shell.php'  | score=90  Block  [WP-UPLOAD-001]
    sent='shell.p{h}p'  -> WP writes 'shell.php'  | score=0   Allow  []
    sent='shell.php-'   -> WP writes 'shell.php'  | score=0   Allow  []
    sent='shell.p%hp'   -> WP writes 'shell.php'  | score=0   Allow  []
    sent='web.con{f}ig' -> WP writes 'web.config' | score=0   Allow  []
    sent='web.config-'  -> WP writes 'web.config' | score=0   Allow  []
    sent='shell.as{p}x' -> WP writes 'shell.aspx' | score=0   Allow  []

web.con{f}ig is the sharpest case: IIS-CONFIG-001 is the 100-point "no false positives expected"
rule, and one brace turns it off. With the <?php marker padded beyond SampleBytes,
PHP-CONTENT-001 is silent too, so the total is genuinely 0 / Allow / not even a Warning. The full
kill chain is one request.

THREAT_MODEL.md:244 says relying on WordPress to call sanitize_file_name() is not a control —
correct, but it only covers the direction where WordPress does too little. The inverse, where
WordPress **creates** the dangerous name, is undocumented and unmitigated.

Suggested fix: add a second normalization view — WordPress's — and evaluate the extension rules
against **both**, most severe wins. That is the same shape as the existing filename/filename*
two-name handling, so aggregation already supports it. FILE-NAME-001 should report a new
wordpressRewrite anomaly so the divergence is visible in Monitor before Block turns it into a
refusal.

### F6 — LOW. Evidence can carry bidi and zero-width characters into a log.
NormalizedFileName.RemoveControlCharacters strips char.IsControl but not U+200B-200F, U+202A-202E,
U+2066-2069. A log consumer or dashboard rendering normalizedName can be made to display something
other than what was uploaded.
